# The form is a data file, and the answer has no form

> Correcting 0236, which read "field definitions" as the input *type*:
>
> "We don't need output fields, but I like input fields to be an .elo/data file
> on its own (that would allow generating an html form easily, even if that
> fields file could partly be generated by static analysis of the input type)"

So the fields file is the **form**, not the schema — and the parenthesis is the
whole design: it may repeat part of the type, because it can be generated from
it.

## What changed

```
iban/
  types.elo       # Input and Output          (unchanged)
  formula.elo     # the doc comment and { formula: … }
  fields.elo      # the input form, as data   ← new
  cases.elo
  bundle.json     # now only metadata: bundle, version, license, tags
```

```elo
{
  fields: [
    {
      path: 'tier',
      label: 'Customer tier',
      type: 'String',
      widget: 'select',
      required: true,
      constraints: ['known'],
      options: ['standard', 'silver', 'gold']
    }
  ]
}
```

`bundle.json` lost its `fields` and `output` presentation blocks: a label
belongs where the form is, and the manifest is now the one file a catalogue can
ignore entirely and still render the formula.

**No output fields.** `Output` stays — it is the promise, and it is applied, so
the answer is checked where it is produced — but there is no form for it and no
labels: an answer is rendered, not filled in. A catalogue that wants its shape
in advance reads `types.elo`.

## The rule, restated

0233 said *nothing may be stated twice*. `fields.elo` breaks that on purpose:
it carries `type`, `required`, `repeated` and `constraints`, which `Input`
already says. The rule becomes **nothing may be stated twice unchecked**:

- `formula-bundle.js --fields <id>` **generates** the file from `Input`, keeping
  every label, widget, option, help and placeholder already written. So the
  derived half is never typed by hand: change `Input`, refresh, fill in labels.
- `checkFieldsAgainstInput` **re-derives** it on every test run and refuses a
  bundle whose file disagrees — a wrong type, a wrong `required`, a missing
  constraint name, a field `Input` does not declare, a field it forgets.
- An integration test asserts, per bundle, that the file **is what the
  generator would write**. Not formatting pedantry: it is what makes `--fields`
  a safe refresh.

What that buys is the thing asked for: **an HTML form is one data file away**.
No AST, no Elo host, no type walking — read `fields.elo`, render the widgets,
post JSON.

## A bonus the move paid for

`options` was the wart 0233 confessed to: a choice is a predicate, so a
dropdown's values were stated twice with nothing checking them. Now that the
options sit next to the field's declared type, the lint can **apply each one**:

```
order-pricing: fields.elo offers 'platinum' for 'tier', which Tier refuses
```

It works where the field's type has a *name* (`tier: Tier`), because a name is
what can be imported and applied on its own — which is a reason to declare a
choice as a named type, and it is how all three choice fields in the catalogue
are written. A field typed inline goes unchecked, and `ideation/0235` (the
literal union type) is still the fix that would remove the duplication
altogether rather than check it.

## Shape of it now

| File | Written by | Checked against |
| --- | --- | --- |
| `types.elo` | hand | the cases, on three targets |
| `formula.elo` | hand | the cases |
| `fields.elo` | generated, then labelled | `Input`, key by key |
| `cases.elo` | hand | the formula, on three targets |
| `bundle.json` | hand | nothing — there is nothing in it to check |

108 integration tests over the format, 39 case runs on JavaScript, Ruby and
Python, and six of the tests break a rule on purpose so the lint is known to
refuse something.
