2. Plan in the page, checks on the server

The server reads the schema into a plan: plain JSON, with each constraint reduced to what a form can say about it. The page builds the form from that. It carries neither Elo nor Luxon and evaluates nothing. Hints, drop-downs and picker bounds are all there; whether a value is accepted is asked of the server, whose answer is shown on the field it is about.

What to copy

  • The page's script: 2-plan.js.
  • From the server: plan() behind /order/plan.json, and check() behind POST /order/check, which answers 422 with Elo's error as it was thrown.

Security profile: the one for schemas from strangers

  • Nothing of the schema ever runs in the browser. A plan is data, and the form shows it as text: no markup, no address, no script can come out of it.
  • Reading the schema runs nothing either: planForm parses. The one place the schema executes is where you already run it to answer.
  • The policy can be as strict as you like.
  • What is left to a hostile schema: saying anything in a label, asking for an email or a password so that the browser offers to fill it in (guessFromNames: false), and being large (maxNodes).
  • The cost is a round trip before a constraint is reported.
