3. Plan, and checks compiled on the server

What a strict policy forbids is turning text into code in the page. So the server does the compiling and serves Elo's checks as a JavaScript module, which the page imports like any other script. The form is then as live as in mode 1 — every constraint, on its field, as it is typed — with no compiler in the browser and no 'unsafe-eval'.

What to copy

  • The page's script: 3-checks.js.
  • From the server: checksModule() behind /order/checks.js, Luxon served at /vendor/luxon.js, and check() all the same: a reader can change anything in their own browser.

Security profile: strict policy, but the schema's code is in your page

  • The compiler is gone from the browser; the compiled code is not. The module holds the schema's constraints as JavaScript and runs with your page's origin, on its main thread. What it can reach is, as in mode 1, what Elo's compiled output can reach.
  • So this is for schemas you wrote or reviewed. For a stranger's schema, serve no checks (mode 2), or decide that Elo's sandbox is the boundary you want, and say so.
  • The policy stays strict: the module is a script from your own origin. Nothing is evaluated from a string.
  • The compiler runs on the schema on your server instead. Compiling does not run the schema; cap the size of what you accept.
  • Elo's output needs Luxon when it runs, so Luxon is in the page.
