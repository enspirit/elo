6. Plan, and compiled checks in a worker

Mode 3 puts the schema's compiled constraints in your page. Here the same module is loaded by a worker instead: the page builds the form from the plan, asks the worker about each value, and shows the answers when they arrive. The form is as live as in modes 1 and 3; the schema's code never runs where the page is.

What to copy

  • The page's script: 6-worker.js. A submit handler awaits form.validated(), since answers come later.
  • From the server: checksModule() as in mode 3, the worker's script at /lib/elo-form.worker.js with its own policy header, and check() all the same.

Security profile: strict policy, and the schema's code is kept away from the page

  • No document, no cookies, no page variables. A worker has none of them. All it exchanges with the page is JSON: values in, verdicts out.
  • No network, if you say so. A worker obeys the policy its own script was served with, not the page's. This one is served with default-src 'none'; script-src 'self': it can import the checks and Luxon from your origin, and cannot fetch anything.
  • It cannot hang the page. A round of questions unanswered after two seconds terminates the worker; the form goes on with enforced: false and the server decides, as in mode 2.
  • What is left: the worker shares your origin, so its storage (IndexedDB, caches) is reachable from it. Keep nothing there that matters, or serve the form's page from an origin of its own.
  • The server's verdict is still the one that counts.
